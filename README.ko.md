# AI가 코드를 짜는 시대, 삼권분립 방식으로 코딩해야 한다

### RGB 개발방법론 (Rules, Guard, Build)

## 핵심 구조

| 현실의 삼권분립 | RGB 개발방법론 | 실제 형태 |
|---|---|---|
| 입법부 | Rules | 헌법 / 법률 / 스펙 |
| 사법부 | Guard | Test Cases |
| 행정부 | Build | Application Code |

## 요약

- AI 시대의 프로젝트는 단순히 코드를 빨리 만드는 것보다, **프로젝트의 질서를 먼저 세우는 것**이 더 중요해졌다.
- 내가 말하는 RGB 개발방법론은 그 질서를 **입법·사법·행정**처럼 나눠서 다루는 방식이다.
- **Rules**는 입법이다. 그리고 Rules는 다시 **추상적인 헌법**, **구체적인 법률**, **구현할 기능을 정의하는 스펙**으로 나뉜다.
- **Guard(Test Cases)** 는 사법이다. Rules를 실제로 어겼는지 판정하고, 프로젝트의 질서를 테스트로 집행한다.
- **Build(Application Code)** 는 행정이다. 실제 서비스 코드, 컨트롤러, 유스케이스, 이벤트 핸들러 같은 애플리케이션 코드는 Rules와 Guard 안에서만 움직인다.
- 여기서 말하는 “과거의 성공한 프로젝트”는 전혀 상업적 성공이 아니다. 내가 말하는 성공은 오직 **아키텍처적 성공**이다.
- 즉 경계가 좋았고, 테스트가 강했고, 기능을 계속 붙여도 쉽게 무너지지 않았던 구조적 성공을 뜻한다.
- **헌법과 법률은 도메인 로직이 아니라 구조 규칙이다.**
- **스펙은 도메인 로직과 구현할 기능을 정의한다.**
- RGB는 한 번 선언하고 끝나는 문서 작업이 아니다. **Rules → Guard → Build → Rules 보강으로 이어지는 반복 루프**다.
- 먼저 Rules를 세우고, 그걸 Guard(Test Cases)로 집행 가능하게 만들고, 그 안에서 Build(Application Code)를 만든다. 그리고 구현 과정에서 드러난 문제를 바탕으로 다시 Rules와 Guard를 보강한다.
- 이 과정 전반을 가능한 한 AI가 최대한 수행하고, 사람은 전체를 검토하고 승인하는 쪽으로 갈 수 있다.
- 결국 RGB는 **AI가 코드를 많이 짜도 프로젝트가 무너지지 않게 만드는 반복 가능한 질서**를 만드는 방법이다.

새 프로젝트를 시작할 때, 클로드 코드나 GPT에게 이런 식으로 말해본 적이 한 번쯤은 있을 것이다.

“A 프로젝트 스타일로 초기 세팅 잡아줘.”  
“컨트롤러는 B 프로젝트 방식으로 맞춰줘.”  
“테스트는 C 프로젝트 스타일을 참고해.”  
“패키지 구조도 예전에 잘 됐던 그 방식으로 가자.”

이건 이상한 일이 아니다. 오히려 너무 자연스럽다.

개발자는 새 프로젝트를 시작할 때 완전한 백지에서 출발하고 싶어 하지 않는다. 예전에 구조가 잘 잡혔던 프로젝트가 하나라도 있었다면, 그 프로젝트의 질서를 다음 프로젝트에서도 최대한 이어가고 싶어 한다. 패키지 경계, 테스트 스타일, 동기·비동기 흐름, 공통 코드의 위치, 실시간 채널의 역할 같은 것들이 한 번 잘 작동한 경험이 있다면, 다시 그 감각을 가져오고 싶은 건 당연하다.

문제는 여기서부터 시작된다.

그 질서가 정말 좋았다고 모두가 느끼고 있었는데, 막상 다음 프로젝트로 넘어오면 다시 비슷한 토론을 처음부터 반복하게 된다. 어디까지를 shared로 둘지, 어느 시점에 이벤트로 넘길지, 다른 도메인을 직접 참조해도 되는지, 테스트를 어디까지 통합으로 끌고 갈지, 실시간 채널에서 어디까지 허용할지 같은 이야기들이 또 나온다. 결국 예전에 분명히 잘해봤던 것인데도, 새 프로젝트에서는 다시 흐려진다.

왜 그럴까.

내 생각에는 이유가 단순하다.  
좋았던 구조가 있었던 것은 맞는데, 그 구조가 **재사용 가능한 질서**로 고정되어 있지 않았기 때문이다.

사람은 기억한다. 하지만 기억은 기준이 되지 않는다.  
팀은 감각을 공유한다. 하지만 감각은 테스트가 아니다.  
AI는 예시를 따라 한다. 하지만 예시는 원칙이 아니다.

그래서 나는 요즘 개발에서 중요한 것이 코드 생산량 그 자체가 아니라, **먼저 질서를 세우는 일**이라고 생각하게 됐다. 그리고 그 질서를 정리하는 가장 단순한 틀로 **RGB 개발방법론**이라는 이름을 붙였다.

RGB는 이렇게 읽으면 된다.

**Rules**: 프로젝트의 질서를 정한다.  
**Guard**: 그 질서를 지키게 만든다.  
**Build**: 그 질서 안에서 구현한다.

조금 더 재밌게 말하면, RGB는 개발의 **삼권분립**이다.

입법은 Rules다.  
사법은 Guard다.  
행정은 Build다.

이 비유가 웃기게 들릴 수는 있다. 그런데 생각보다 잘 맞는다.

## 왜 이런 생각을 하게 됐나

AI 시대의 개발자가 원하는 것은 사실 복잡하지 않다.

가능하면 LLM이 많은 구현을 해줬으면 좋겠다.  
기능 추가는 빨랐으면 좋겠다.  
테스트는 충분했으면 좋겠다.  
코드 품질도 유지됐으면 좋겠다.  
그리고 기능을 계속 붙여도 프로젝트가 철학과 원칙을 잃고 무너지지 않았으면 좋겠다.

여기에 하나가 더 있다.

한 번 잘 만들었던 구조를, 다음 프로젝트에서도 다시 쓰고 싶다.

여기서 말하는 “잘 만들었던 구조”는 매출이 잘 나왔다는 뜻이 아니다. 사용자가 많았다는 뜻도 아니다. 투자받았다는 뜻도 아니다. 그런 성공도 물론 중요하겠지만, 여기서 내가 말하고 싶은 건 그게 아니다.

내가 말하는 성공은 **아키텍처적 성공**이다.

경계가 잘 나뉘어 있었다.  
의존성이 건강했다.  
공통 코드가 덜 오염됐다.  
테스트가 구조를 지켜줬다.  
기능을 계속 붙여도 프로젝트가 쉽게 무너지지 않았다.  
AI가 많은 구현을 해도 코드 퀄리티가 크게 흔들리지 않았다.

이런 성공이다.

개발자가 과거 프로젝트를 참고하고 싶어 하는 이유도 결국 이거다. “저 프로젝트는 구조가 좋았어.” “저 프로젝트는 테스트가 진짜 질서를 지켜줬어.” “저 프로젝트는 AI가 많이 만들었는데도 이상하게 안 무너졌어.” 이 감각을 재현하고 싶은 것이다.

그런데 이 욕망은 대개 애매한 말로만 남는다.

“그때 shared를 잘 나눴지.”  
“그때 도메인 경계가 좋았지.”  
“그때는 직접 의존을 잘 막았지.”  
“그때 테스트가 좋았지.”

이런 말은 회고에는 좋지만, 다음 프로젝트의 기본 법질서가 되지는 못한다.

## “그 상식을 누가 모르나요?”

“테스트는 독립적으로 돌아가야지 ㅋㅋ”  
“도메인끼리 직접 물리면 나중에 꼬이지.”  
“공통 코드는 shared로 빼야지.”  
“비동기 흐름은 이벤트로 가는 게 낫지.”  
“SSE에서 상태 바꾸면 좀 이상하지 않나?”

이런 말들은 개발자에게 너무 익숙하다.  
낯설지도 않고, 대단한 통찰처럼 들리지도 않는다.

그리고 이어서 이렇게 말할 수 있다.

**“그 상식을 누가 모르나요?”**

맞다. 대부분의 개발자는 이미 알고 있다. 이건 새로운 진리가 아니다. 거의 상식에 가깝다.

그런데 바로 그 점이 문제다.

상식은 보통 문서로 남지 않는다.  
문서로 남지 않으면 기준이 되지 않는다.  
기준이 없으면 바쁠 때 타협된다.  
타협이 반복되면 예외가 쌓인다.  
예외가 쌓이면 구조가 무너진다.

즉 문제는 상식이 없어서가 아니다.  
문제는 **상식이 머릿속에만 있어서**다.

그래서 필요한 것은 “좋은 생각”이 아니라,  
**짧고 강한 규칙으로 고정된 생각**이다.

RGB에서 그게 바로 Rules다.

## 헌법과 법률은 비즈니스 로직이 아니다

여기서 꼭 먼저 분리해야 할 것이 있다.

예전처럼 **“Rules는 비즈니스 로직이 아니다. Rules는 도메인 로직이 아니다.”** 라고 한 덩어리로 말하면, 지금의 RGB 정의와는 정확히 맞지 않는다. 왜냐하면 이제 Rules 안에는 **스펙**이 들어가고, 스펙은 실제로 **무엇을 구현할 것인가**, 즉 도메인 로직과 기능 요구를 정의하기 때문이다.

그래서 더 정확하게 말하면 이렇다.

**헌법과 법률은 비즈니스 로직이 아니다.**  
**헌법과 법률은 도메인 로직이 아니다.**  
**스펙은 도메인 로직과 구현할 기능을 정의한다.**

회원가입 정책, 할인 정책, 정산 계산식, 포인트 소멸 규칙 같은 것은 구조 규칙이 아니다. 그건 도메인이다. 그건 서비스마다 달라지고, 제품마다 달라진다.

RGB에서 내가 말하는 **헌법과 법률**은 그보다 위에 있는 것이다.  
즉 **프로젝트가 어떤 질서 위에서 움직여야 하는지**를 정하는 구조 규칙이다.

예를 들면 이런 것들이다.

도메인은 명확한 경계를 가진다.  
도메인 간 직접 의존을 금지한다.  
공통 코드는 공통 영역에 둔다.  
동기 호출은 정해진 경로를 통해서만 한다.  
비동기 흐름은 이벤트로 처리한다.  
테스트는 독립적으로 실행 가능해야 한다.  
실시간 채널은 읽기 전용으로 사용한다.

이건 기능 규칙이 아니라 **구성 규칙**이다.  
프로그램이 어떤 질서 위에서 움직여야 하는지를 정하는 규칙이다.

반면 스펙은 이런 것을 다룬다.

회원 가입 API  
게시글 작성  
좋아요 기능  
정산 배치  
알림 발송  
검색 기능

즉 RGB에서 Rules는 하나의 단일 규칙 문서가 아니다.

- **헌법**: 구조 철학
- **법률**: 구조 규칙
- **스펙**: 도메인 로직과 구현할 기능

이 구분이 선명해야 RGB도 선명해진다.

## Rules 단계는 왜 헌법·법률·스펙으로 나뉘어야 하나

여기서 Rules를 단순한 규칙 리스트로만 보면 중요한 부분을 놓치게 된다.

Rules 단계는 한 층이 아니다.  
현실 세계에서 입법이 단순한 규칙 목록이 아닌 것처럼, 프로젝트의 Rules도 **추상적인 헌법**, **구체적인 법률**, **구현할 기능을 정하는 스펙**으로 나뉘어야 한다.

먼저 헌법이 있다.

이건 가장 위의 원칙이다.  
모든 구체 규칙보다 위에 있는 방향이다.

예를 들면 이런 식이다.

도메인은 명확한 경계를 가진다.  
도메인 간 직접 의존을 금지한다.  
공통 코드는 공통 영역에 둔다.  
실시간 채널은 읽기 전용으로 사용한다.

이건 꽤 추상적이다.  
그런데 바로 그 추상성 때문에 중요하다.  
구체적인 규칙이 아직 다루지 않은 상황이 생겨도, 헌법이 방향을 준다.

그다음에 법률이 있다.

이건 헌법을 실제 프로젝트 규칙으로 내린 것이다.

예를 들면 이런 식이다.

동기 호출은 API Client를 통해서만 한다.  
비동기 흐름은 Event로 처리한다.  
shared에는 도메인 엔티티나 도메인 정책을 두지 않는다.  
테스트 환경에서는 비동기 처리가 결정론적으로 검증 가능해야 한다.

그리고 이제 여기에 스펙이 추가된다.

스펙은 헌법이나 법률과 다르게 **무엇을 만들 것인가**를 정의한다.

예를 들면 이런 식이다.

회원 가입 API를 만든다.  
게시글 작성 기능을 만든다.  
좋아요 기능을 만든다.  
알림 시스템을 만든다.  
검색 기능을 만든다.

즉 Rules 단계는 “규칙 몇 개 적어두기”가 아니다.  
**추상적인 헌법**, **구체적인 법률**, **구현 대상을 정의하는 스펙**으로 나뉜 구조다.

왜 굳이 이렇게 나누는가.

이유는 서로 역할이 다르기 때문이다.

세부 규칙이 비어 있을 때는 헌법이 방향을 준다.  
구체적인 구현 단계에서는 법률이 행동 기준이 된다.  
실제 개발을 진행할 때는 스펙이 구현 목표를 준다.

그리고 이 셋은 변화의 속도도 다르다.

헌법은 가장 천천히 바뀐다.  
법률은 프로젝트에 맞게 조정된다.  
스펙은 가장 자주 바뀐다.

그래서 이 셋을 분리해두는 편이 훨씬 강하다.

한 문장으로 줄이면 이렇게 된다.

**헌법과 법률은 어떻게 만들 것인가를 정의하고, 스펙은 무엇을 만들 것인가를 정의한다.**

## 왜 LLM 시대에 더 잘 맞는가

이 구조가 좋은 이유는 사람 때문만은 아니다.  
오히려 AI 때문이다.

LLM은 긴 문단 속에 흐릿하게 녹아 있는 의도보다, 짧고 분리된 원칙 문장을 훨씬 잘 따른다.

“도메인 간 상호작용은 상황에 맞게 적절히 느슨하게 유지하는 것이 좋다.”

이런 문장은 사람도 대충 이해하고 넘어간다. AI도 대충 이해한다.  
문제는 “대충”이다.

반면 이런 문장은 다르다.

도메인 간 직접 의존을 금지한다.  
동기 호출은 정해진 경로를 통해서만 한다.  
비동기 흐름은 이벤트로 처리한다.

이건 사람에게도 강하고, LLM에게도 강하다.

게다가 “다음 규칙들을 참고해”보다  
“다음은 이 프로젝트의 헌법이다. 다음은 이 프로젝트의 법률이다. 다음은 이 프로젝트의 스펙이다.”  
라고 말하는 편이 더 강하게 작동할 가능성이 크다.

LLM은 이름과 위계를 꽤 민감하게 해석한다.  
그래서 헌법, 법률, 스펙이라는 표현은 단순한 장식이 아니라,  
**규칙의 위계와 구현의 방향을 전달하는 인터페이스**가 된다.

---

## Guard는 사법부다

입법만 있다고 시스템이 굴러가지는 않는다.

현실에서도 법을 만들기만 하고, 위반 여부를 판단하는 기관이 없다면 법은 문서에 불과하다. 프로젝트도 마찬가지다.

Rules가 문서에서 끝나지 않게 만드는 것이 Guard다.

Guard는 테스트, 아키텍처 체크, 패키지 의존성 검사, 통합 검증, 제약 검증 같은 것들을 포함한다. 핵심은 단순하다.

**이 규칙을 어기면 실패해야 한다.**

다른 도메인을 직접 참조했는가.  
읽기 전용 채널이 상태를 바꾸는가.  
공통 영역이 도메인 로직을 먹어버렸는가.  
테스트가 더 이상 독립적으로 돌지 않는가.  
비동기 흐름이 검증 불가능해졌는가.

Guard는 이런 걸 판정한다.

그래서 Guard는 단순한 테스트 묶음이 아니다.  
**프로젝트의 사법부**다.

테스트는 “기능이 맞았네”로 끝나는 도구가 아니다.  
잘 만든 Guard는 “이 구현이 Rules를 위반했는가”를 판결하는 장치다.

---

## Build는 행정부다

마지막이 Build다.

Build는 실제 구현이다.  
컨트롤러, 유스케이스, 서비스, 도메인 메서드, 이벤트 핸들러, 스케줄러, 실시간 전송 코드 등이 여기에 들어간다.

즉 Build는 실제로 일을 한다.  
하지만 아무렇게나 일하지 않는다.

Rules가 위에 있고, Guard가 옆에 있다.  
Build는 그 질서 안에서만 움직인다.

그래서 Build는 그냥 코딩이 아니라,  
**Rules와 Guard 아래에서 집행되는 행정**이다.

이 비유가 좋은 이유는 각 역할이 섞이면 안 된다는 점까지 보여주기 때문이다.

실행 코드가 자기 멋대로 규칙을 만들면 안 된다.  
Guard가 Rules 없이 기능만 체크해서도 안 된다.  
Rules가 없는데 Build만 커지면 사실상 무법 상태가 된다.

좋은 프로젝트는 단순한 코드 집합이 아니다.  
조금 재밌게 말하면, **입법·사법·행정이 분리된 작은 국가**에 가깝다.

---

## 실전 방법론: RGB는 반복된다

RGB는 선언문이 아니다.  
실전에서는 **반복 루프**로 돌아야 한다.

### 1. Rules 단계

먼저 현재 프로젝트에 필요한 질서를 정한다.  
그리고 이 단계에서 다루는 것은 세 가지다.

- **헌법**: 가장 추상적인 최상위 원칙
- **법률**: 그 헌법을 실제 프로젝트 규칙으로 내린 구체 규칙
- **스펙**: 구현해야 할 기능과 도메인 로직

즉 Rules 단계는 그냥 체크리스트가 아니라,  
**구조 철학과 구조 규칙, 그리고 구현 목표를 함께 정리하는 단계**다.

구현을 하다 보면 이 셋은 계속 보강된다.

- 헌법이 너무 모호했을 수 있다.
- 법률이 비어 있었을 수 있다.
- 스펙이 덜 정리되어 있었을 수 있다.

그래서 Rules 단계는 한 번 정의하고 끝나는 단계가 아니라  
**정의/개선이 반복되는 단계**다.

### 2. Guard 단계

그 Rules가 문서에서 끝나지 않도록,  
테스트 케이스와 각종 검증 장치로 바꾼다.

핵심은 단순하다.

**이 규칙을 어기면 테스트가 실패해야 한다.**

그래서 Guard는 단순한 테스트 모음이 아니라,  
프로젝트의 **사법부** 역할을 한다.

여기서 중요한 점이 하나 있다.

**Guard 단계에서는 Test Cases를 통해 그 질서가 실제로 지켜지는지 판정하고 집행 가능하게 만든다.**  
즉 테스트 케이스를 추가하고 발전시킨다.  
그리고 **새롭게 추가된 테스트는 처음에는 실패하는 것이 정상이다.**

그 실패는 문제가 아니라,  
오히려 질서를 새로 명문화했다는 뜻이다.

### 3. Build 단계

이제 실제 애플리케이션 코드를 만든다.

컨트롤러, 유스케이스, 서비스, 도메인 메서드, 이벤트 핸들러, 스케줄러 같은 실제 실행 코드는 모두 여기에 들어간다.

중요한 점은 이것이다.

**Application Code는 Rules와 Guard 안에서만 움직여야 한다.**

즉 Build는 그냥 코딩이 아니라,  
프로젝트의 **행정**이다.

그리고 더 직설적으로 말하면, Build 단계에서는  
**테스트를 통과하도록 코드를 작성하고 시스템을 점진적으로 완성한다.**

### 4. 다시 Rules와 Guard를 보강한다

구현을 진행하다 보면 드러나는 것들이 있다.

- 헌법이 너무 모호했다
- 법률이 비어 있었다
- 스펙이 덜 정리되어 있었다
- Test Cases가 질서를 제대로 못 지켰다
- Application Code가 예상 밖의 구조 문제를 드러냈다

그러면 다시 Rules를 수정하고,  
Guard(Test Cases)를 보강하고,  
그다음 Build(Application Code)를 다시 진행한다.

즉 RGB는 이렇게 돈다.

**Rules → Guard(Test Cases) → Build(Application Code) → Rules 보강 → 다시 반복**

이 점에서 RGB는 한 번 적용하고 끝나는 방식이 아니라,  
**계속 반복하면서 프로젝트의 질서와 구현을 함께 강화하는 루프**다.

---

## RGB는 사람이 다 하는 절차가 아니다

여기서 또 하나 중요한 전제가 있다.

RGB는 사람이 모든 걸 직접 수행하는 절차가 아니다.  
오히려 가능한 한 **AI가 최대한 수행**한다.

AI가 Rules 초안을 만든다.  
AI가 Guard를 만든다.  
AI가 Build를 한다.  
AI가 구현 과정에서 드러난 문제를 바탕으로 다시 Rules와 Guard를 보강한다.  
사람은 전체를 검토하고 승인한다.

즉 사람의 역할은 줄어든다기보다 바뀐다.

사람은 가장 많이 코딩하는 사람이 아니라,  
**AI가 만든 규칙과 구현이 프로젝트의 질서를 제대로 지키는지 최종 판단하는 사람**에 가까워진다.

내가 보기에 앞으로 개발자의 실력은 점점 여기로 이동할 가능성이 크다.

좋은 Rules를 만들 수 있는가.  
좋은 Guard 장치를 세울 수 있는가.  
그 질서를 AI와 함께 계속 발전시킬 수 있는가.  
그걸 다음 프로젝트로 전승할 수 있는가.

이게 점점 더 중요한 역량이 될 수 있다.

---

## 프로젝트마다 매번 새로 만드나

이 질문도 자연스럽게 나온다.

“그러면 프로젝트를 할 때마다 Rules를 새로 만들어야 하나요?”

내 생각은 대체로 아니다.

헌법과 법률은 도메인 지식이 아니라 구조적 질서다.  
그래서 상당 부분 재사용된다.

좋은 헌법은 재사용된다.  
좋은 법률은 템플릿이 된다.  
좋은 Guard는 반복해서 쓸 수 있다.  
좋은 Build 패턴은 팀의 기본값이 된다.

스펙은 프로젝트마다 달라질 수 있다.  
하지만 그 스펙을 담아내는 구조 질서는 재사용될 수 있다.

결국 시간이 지나면 이렇게 된다.

새 프로젝트는  
“또 처음부터 잘해보자”가 아니라  
**“이미 잘해본 질서를 가져오자”** 로 시작된다.

이게 RGB의 진짜 가치다.  
한 번 잘 만든 아키텍처적 성공을, 다음 프로젝트에서도 다시 재현할 수 있게 만든다는 점이다.

---

## 마지막으로

RGB 코딩방식은 전혀 새롭지 않다.

좋은 팀은 원래 경계를 신경 썼고, 테스트를 신경 썼고, 구조를 신경 썼다.  
달라진 건 이제 그 질서를 **AI까지 포함해서 운영해야 한다**는 점이다.

예전에는 좋은 규칙이 있으면 팀이 덜 망가졌다.  
지금은 좋은 규칙이 있으면 **AI까지 덜 망가뜨린다.**

---

## 결론

RGB 개발방법론은 AI 시대의 소프트웨어 개발에서 먼저 프로젝트의 질서를 세우고 그 질서를 반복적으로 발전시키기 위한 접근이다.

Rules 단계에서는 헌법·법률·스펙을 정의/개선하여 프로젝트의 구조 질서와 구현할 기능을 정리한다. 즉 프로젝트의 구조 원칙과 구현 목표를 명확히 한다.

Guard 단계에서는 Test Cases를 통해 그 질서가 실제로 지켜지는지 판정하고 집행 가능하게 만든다. 즉 테스트 케이스를 추가/발전시킨다. 새롭게 추가된 테스트는 처음에는 실패하는 것이 정상이다.

Build 단계에서는 그 질서 안에서 실제 Application Code를 구현한다. 즉 테스트를 통과하도록 코드를 작성하고 시스템을 점진적으로 완성한다.

이 반복 루프를 통해 스펙의 깔끔한 구현과 아키텍처의 견고함을 지속적으로 유지하고 발전시킨다.
